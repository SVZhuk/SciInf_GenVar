# Week 1: Project setup, CI and the Projects API

Build the foundation of the Genomic Variant Analysis Platform: a FastAPI service backed by
PostgreSQL that users will later use to upload VCF files, filter and annotate variants and get
summaries. See [ARCHITECTURE.md](ARCHITECTURE.md) for the target picture; you fill in its empty
sections as part of this task.

## Tasks

### 1. Project setup
1.1 Initialize a Git repository on GitHub.
1.2 Set up the project structure: API route handlers, services, models, schemas, database session.
1.3 Set up a virtual environment using Poetry.
1.4 Install core dependencies and create a base FastAPI application.
1.5 Set up Docker and Docker Compose for local development.
1.6 Write a `README.md` with setup instructions.

### 2. CI pipeline
2.1 Set up a GitHub Actions workflow:
- Pipeline stages: linting, formatting, tests.
- CI runs on every push and every pull request.
- Configure pre-commit hooks locally: ruff, trailing whitespace, end-of-file fixer.

### 3. Initial endpoints
- `POST /projects/`: create a new project
- `GET /projects/`: list all projects
- `DELETE /projects/{project_id}/`: delete a project

### 4. Database design (PostgreSQL)
4.1 Design a relational schema for projects, uploaded VCF files, parsed variants, uploaded
annotation files and variant annotations: at least `projects`, `vcf_files`, `variants`,
`annotation_files` and `annotations`. Put the design (ER diagram plus key decisions) in
`ARCHITECTURE.md` section 6. **Implement only the `projects` table this week**; the other tables
are added in later weeks.

4.3 Connect the project endpoints to PostgreSQL through the SQLAlchemy async ORM.
4.4 Create SQLAlchemy models matching the schema.
4.5 Create Pydantic schemas for request and response validation.
4.6 (Optional) Set up Alembic for database migrations.

## The `projects` table

| Column | Type | Rules |
|---|---|---|
| `project_id` | UUID, primary key | Generated by the server; clients cannot set it |
| `name` | text, max 100 | Required, unique; a duplicate returns 409 Conflict |
| `lead_scientist` | text, max 100 | Required |
| `description` | text | Optional |
| `created_at` | timestamp with time zone | Set by the database when the row is inserted |
| `completed_at` | timestamp with time zone | Empty until the project is finished; not settable this week |

Naming conventions are in [ARCHITECTURE.md](ARCHITECTURE.md#6-data-model) section 6.

## Assessment criteria

1. **Functional:** all tasks are done; the application builds and runs without errors.
2. **Clean code:** follows SOLID, KISS and DRY, uses appropriate design patterns, and is well
   organised.
3. **Logging:** used throughout, with the right levels (DEBUG, INFO, WARNING, ERROR), enough
   detail to diagnose problems, and no sensitive data (credentials, database URLs, request bodies,
   VCF content).
4. **Tests:** line coverage at least 80%, and tests follow the FIRST principles (Fast,
   Independent, Repeatable, Self-validating, Timely).
5. **Task-specific criteria.** The rubric is worded for Java; in this Python project it means:
   - **"Bean configuration"**: dependency injection with FastAPI `Depends` (with `Annotated`
     aliases). Wire it in one place, so tests can swap a dependency through
     `app.dependency_overrides`.
   - **"In-memory storage implemented correctly and optimally"**: an in-memory storage class with
     the same methods as your database storage, backed by a dict keyed by id so lookups are O(1).
     Use it in fast tests that need no database.
   - **"Usernames generated correctly, without duplication"**: identifiers are generated by the
     server (UUIDs), and project names are unique, enforced by a database constraint, with a
     duplicate returning 409 Conflict.

## Tests

- Unit and API tests use the in-memory storage: no database, milliseconds per test.
- Integration tests run against a real Postgres in Docker (a separate test database service in
  Docker Compose locally, a Postgres service container in CI). Roll back each test's transaction
  so tests do not affect each other.
- Do not mock the database session: mocked SQLAlchemy calls test the mock, not your SQL.
- The 80% coverage is measured over the whole suite.
